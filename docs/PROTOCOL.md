# 制作プロトコル v3（2026-10-14。これが正本）

一話を、一行の案から採用まで通す手順。手順と決まりはここに全部書く。`skills/` の各ファイルは、この文書の段ごとの手の動かし方（付録）で、ここと食い違えばここが正。経緯は `docs/HISTORY.md`。
組み直しの根拠は作品の research/protocol-v3-2026-10-14.md（kyuketsu-mahou-syojo04）。

## 0. 原則（六つ）

1. **決まりは機械か一枚の紙で保証する。** 呼び方・口調・表記・NG・数字・再演・決定との照合は、`check_episode`／`check_reuse`／`check_decisions` が見るか、決まりごと一枚（RULES）に載せる。LLM の点検に決まりの監視をさせない。
2. **面白さはオーナーが二度だけ見る。** 一行の案（読みたい）と、初稿の場面（○△×）。点検は間違いを見つける係で、面白さを見ない。
3. **点検は提案、直すのはオーナーが選んだものだけ。** 自動で直さない。「必須を全部埋める」の関門は置かない。機械の ERROR・NG・再演・封印だけは書き手が直してよい（何を直したか一覧で報告）。
4. **渡すものは生成する。** 書き手の束も点検の束も `pack.py` が作る。束に入っていないものは読まない。
5. **一話の LLM の点検は六回まで。** メモ 1・初稿の筋 1＋声 1・採用前の筋 1・読者 1（二人目はオーナーが要るときだけ）・波及 1。差分の点検は場面の順が変わったときだけ 1。判定役・まとめ役は置かない。
6. **禁止の一覧を作らない。** オーナーの直しは「決まり」（RULES に一行）か「事実」（台帳）か「一回限りの好み」（preferences に記録）に分け、束にして渡さない。

## 3. 各段の決まり

### 3-1. 一行の案
一話の枠ごとに 8〜10 本。形は「事件／主人公が自分からすること／攻略の材料／外の反応／引き」。主人公が自分からすることは行動（見る・待つ・受ける、は行動ではない）。一話に束ねるのは一本。引きに使う一本を足してよい。動かさないもの（公開済み・章の決定）を案の前に一覧にする。市場の型・推奨の一択で絞らない。オーナーの印はチャットで（「26-1: ○」）。書き手が md の表に写してコミット。選ばれるまで散文にしない。

### 3-2. 散文のあらすじ
選ばれた一行を 400〜600 字の散文で（誰がどこで何をして、誰が何を知るか、見せ場の台詞 1〜2 行、引き）。台詞はそれ以外確定しない。地の文の声は書かない。作者の判断（持ち場・引き・設定の分かれ目）はここで二択にしてオーナーに出す。整合のために説明を足さない（読者が常識で補うことは書かない）。

### 3-3. メモ
templates/work/blocks/BLOCK-MEMOS.md の形。見せ場の台詞 2〜3 行、引き、誰が何を知るか、場面ごとの「本当に気にしていること」と運び（掛け合い／地の文）。確定文の一覧・回収の一覧・字数の指定は書かない。機械が読む欄を必ず書く：視点・型・出る人物・world・検索語（触れない）・検索語（使わない）。前の話の仕草・言い回しは採用版を grep して 2 回以上なら使わない。作者が体験していない現場の段取りは書かない。

### 3-4. 束
- 書き手の束（`pack.py EPxxx --writer`）：RULES → WRITE-BRIEF → 同じ型の採用話一本 → 出る人物のカード → world の節 → 散文とメモ → 直前話 → layout と style の要点。これ以外は読まない（工程の文書・HANDOFF・AGENTS・前の版・対応表・LONG-ARCS・台帳の記録は入れない）。
- 点検の束（`pack.py EPxxx Vn --check`）：RULES・カード・知っていること・world の節・前の話までのあらすじ・前の話・散文とメモ・本文。約 3 万字。筋・差分・採用前の点検は全部これ。

### 3-5. 初稿
角度を変えて二本、全文。各場面にメモにない発明を一つ。地の文の塊は報告で終わらない（WRITE-BRIEF）。字数は作品の下限（pachi.json min_chars）。採用前の版は場面の頭に「◇場面N」の仮の印。書いたら `sync_current.py`。

### 3-6. 点検（機械と LLM の分担）
- 機械（毎版、無料）：`check_episode`（表記・行・リズム・NG・数字・AIっぽい型・警報・地の文の敬称）、`check_reuse`（再演・封印・一話の中の重なり）、`check_decisions`（見せ場の台詞・引き・触れないこと・出る人物・知らない言葉の候補・口調の候補・台詞に必ず出る語・場面の台詞の量）。
- 筋（LLM）：事実（前の話との矛盾・話の中の破綻）・誰が何を知る・話し手・立場・指示語・人の動き・決定、参考に読者が知らない言葉。散文の運びとの違い・現場の細部・つながり・読み・数字は挙げない。
- 声（LLM。初稿だけ）：AIっぽい・書きすぎ・言葉と物・数字・説明（読者が常識で補えることを言っている文）。場面の良し悪しは見ない。
- 出し方：行ごとに「今の文／案A／案B／推奨／重要度」。`check_all` が機械・筋・声を一枚にし、先頭に重要度順の「オーナーへの報告」を置く。書き手は行ごとに「直す：案Aで／直す：別の形で／そのままでよい：理由」を埋めてチャットに出す。判断は、本文で今何が成立しているか、補足で何を失うかを確かめてから。オーナーは番号で選ぶ。入れるのは選ばれたものだけ。
- 差分の点検（`--base`）は、場面の順・人物の配置・誰が何を知るかが変わった直しのときだけ。行の直し・磨き・ならしにはかけない。

### 3-7. 場面の印と直し
オーナーは推奨の一本を読み、場面ごとに ○／△（一言）／×。行の指摘はしない。× はもう一本の同じ場面と差し替えるか、角度を一言指定して書き直す（一場面につき一回。二回目も × なら散文に戻す）。△ は一言に沿って場面単位で直す。全部 ○ になるまで磨かない。

### 3-8. 磨きとならし
場面が全部 ○ になってから。磨きは WRITE-BRIEF の形（a→b→c／d→f）と layout に沿って書き手が一度で。ならしは読点・改行・段落の結合だけ、全文一回。合格は機械の［警報］が鳴らないこと。オーナーが書いた文は一字も直さない（episodes/EPxxx/notes/owner-lines.md に記録。点検で引っかかったら直さず報告）。

### 3-9. 直し案（オーナーが行を指摘したとき）
作品の fix-line の手順。案は「たたき（未点検）」か「案 A／B・推奨」で見せ、選ばれた案だけを `propose.py` で機械の点検にかけて番号（P…）を付け、`--apply` で入れる。手で打ち直さない。本文で台詞や筋を変えたら同じコミットで散文とメモに写す。コミットの件名に `(owner:A〜F)`。詳しい手は `skills/revise-episode.md`。

### 3-10. 採用の記録
`skills/finalize-episode.md`。summary.md、台帳カードの書き直し（今の距離と反応・呼び方・もう使わない反応は MOTIFS へ）、記録の「知っていること」、SYNOPSIS に 2〜3 行、MOTIFS の更新、foreshadow、HANDOFF の「写していない決定」の欄が空か確かめる。そのあと波及の確認（`check_memo.py --after`。食い違いと受け渡しだけ。回収の提案は入れない）。

## 4. 版とコミット
- 版は上書きしない。直すときは新しい番号で保存し、`sync_current.py`。
- 採用は notes/summary.md の「採用版：Vn」で表す。current は採用を表さない。
- GitHub の main が正。区切りごとに commit して push。クラウドのセッションも main に直接。
- HANDOFF.md は上書き（20 行以内）。履歴は git log と summary に任せる。

## 5. 伏線の台帳
状態：予定 → 張った → 補強 → 回収済、または 破棄。張った・補強・回収済は採用本文の話番号を根拠に更新する。回収は元の伏線 ID を指す。破棄はオーナーの決定を changes.md に記録する。回収の予定を次の話のメモに流し込まない（回収するかは一行の案でオーナーが決める）。

## 6. 設定変更
concept・canon・既出の事実を変えるときは changes.md に、日付・変更・理由・影響する話を書く。既出話と矛盾する場合は、既出話を直すか本文で説明するかをオーナーが決める。

## 7. 採用済みの話を改稿するとき
新しい版 V(n+1) を作り、`sync_current.py`。機械の点検と `check_all --final`。オーナーが採用したら summary の「採用版」を更新。確定していた事実が変わるなら changes.md と後続話の確認。

## 8. 章末（skills/chapter-review.md）
通し読み（設定資料を渡さない読み手）、伏線の棚卸し（threads.py）、反復の点検、正典の整理、次章の背骨と各話の散文（check_memo をかけてからオーナーが通しで読む）。

## 9. 測るもの
一話あたり、オーナーが全文を読んだ回数と版の数（目標：版 3〜5、通読 1〜2 回）。LLM の点検の回数（上限六回）。オーナーの指摘で直したコミットの `(owner:A〜F)` は `interventions.py` で数える（主な物差しにしない）。
