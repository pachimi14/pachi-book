# write-episode：1話を書く

作品リポジトリのルートで行う。成果物は、ブロックのメモ（`blocks/` の BLOCK-MEMOS 形式）と新しい版 `episodes/EPxxx/Vn.md`、点検の対応表 `episodes/EPxxx/notes/check-Vn.md`。
`episodes/EPxxx/` 直下には版の本文（Vn.md）だけを置き、メモ・点検・要約は `notes/` に置く。台帳はまだ変えない。版を作るたびに `python ../pachi-book/scripts/sync_current.py` で `episodes/current/` を最新版にする。

この手順は 2026-10-01 のオーバーホールで組み直した。9/30 の記録では、オーナーの介入の約3割が「本文を読んでから決め直した筋・配置」、約1割が「作者が体験していない現場の細部」で、そのたびに磨いた文が捨てられていた。決めることはメモで決め、文を磨くのは筋が決まってからにする。

## 0. セッション
1話（またはブロック）ごとに新しい会話で始める。長い会話は、一往復ごとに文脈全体を読み直すので使用量が膨らむ（9/28〜10/1 の会話は、使用量の約7割が文脈の読み直しだった）。引き継ぎは台帳・メモ・各話の summary に任せる。

## 1. メモ（ブロック単位。本文より先）
1. `templates/work/blocks/BLOCK-MEMOS.md` の形で、ブロックの全話のメモを作る。各話に、面白いところ・報酬・芯・場面ごとの「主人公が本当に気にしていること」・見せ場の台詞・引き・**オーナーが選ぶ（二択）**・**現場**。
2. `python ../pachi-book/scripts/check_memo.py <メモ>`。「書く前に必ず直す所」を直し、「オーナーに聞く二択」をメモの「オーナーが選ぶ」に足す。
3. オーナーに見せるのは、芯・見せ場の台詞・引き・二択・現場の欄だけ。二択に答えてもらってから本文へ。
   - 現場の欄で「先に調べる」になった場面は、`research/` に調べたことを置いてから書く。調べないなら、人と気持ちだけで書き、段取り・係の動き・業界の言葉は書かない。

## 2. 書く前に読む
1. 作品の AGENTS.md が指定する良い例と文体の見本（禁止・注意の一覧は書く前には読まない。書いたあとの点検で使う）。
2. `../pachi-book/skills/layout.md`（行・空行・表記の既定）。
3. その話のメモ、直前話の採用版の本文、`canon/` のうち登場人物と使う能力の項。

## 3. 温度の確認（一場面だけ）
見せ場の一場面だけを書き、オーナーに見せる。温度（声・笑い・距離感）が合ってから全文へ。
この段階で、オーナーが筋や配置を変えたら、メモを直してから全文を書く（一場面の文を磨き続けない）。

## 4. 全文を書いて点検する
1. 全文を新しい版 `Vn.md` に保存し、`sync_current.py`。
2. `python ../pachi-book/scripts/check_episode.py episodes/EPxxx/Vn.md`。ERROR は直す。
3. `python ../pachi-book/scripts/check_all.py EPxxx Vn`。機械・筋・声（2回）の点検をまとめた対応表が `notes/check-Vn.md` にできる。表は「必須」と「参考」に分かれている。
4. 「必須」（事実・筋・読者が一度で詰まる所）は一行ずつ、直すか直さないかを決めて「対応」を埋める。直した文は新しい版にする。
   - 点検は直す方向だけを言う。直した文は自分で考え、元の場面の中で読み直す。
   - 直さない行には理由を一言（意図した型、オーナーの決めたこと、など）。
5. 「参考」（文体・型・比喩・書きすぎ・リズム）は、直すかどうかを書き手が選ぶ。全部に従わない。
   2026-10-01 の実験：対応表の全行に従って直すと本文が4割長くなり、オーナーの直し（字数は前後5%ほど）から離れた。必須だけなら字数はほぼ変わらなかった。
6. `python ../pachi-book/scripts/check_episode.py episodes/EPxxx/V(n+1).md --base episodes/EPxxx/Vn.md` で、直しで字数が増えすぎていないかを見る（+10% で警告）。
7. `python ../pachi-book/scripts/check_all.py EPxxx Vn --status` で、必須の対応が空の行が 0 になっていることを確かめる。
8. 面白さは点検では決めない。2026-10-01 の実験で、LLM の判定役はオーナーの版を選べなかった（10回中5回。オーナーが削る「ファンらしい一言」をむしろ好んだ）。点検で直した場面は、元の文と直した文の組でオーナーに見せ、面白さの判断はオーナーがする。
   声の割合（作品の機械点検）も目安にとどめる。オーナーの直しでは、声の割合はむしろ下がっていた。

## 5. 初見読者レビュー（採用前の最後に一回）
`python ../pachi-book/scripts/check_reader.py EPxxx Vn`。【分からない】は直す（新しい版）。【思い出せない】は一言添えるか、そのままにするかを決める。

## 6. オーナーへの報告
全文の前に：見せ場の抜粋3か所／引きの数行／迷ったところ（二択）／対応表の要約（必須を何行直し何行直さなかったか、その理由）／点検で直した場面の一覧（元の文と直した文の組）。

## 7. オーナーの指摘を受けたら
- 指摘はなるべくまとめて受ける（一行ずつの往復は、そのたびに文脈を読み直す）。
- 直し方は作品の fix-line 手順に従う。案を出すときは `python ../pachi-book/scripts/check_logic.py EPxxx Vn --old "元の文" --new "案"` にかける。
  この点検は「直す」に寄りがち（2026-10-01 の検証：オーナー自身の文にも半分は「直す」と出た）。理由が当たっているかを読んで判断する。
- オーナーの指摘で直したコミットの件名に、分類を付ける：`(owner:A)`〜`(owner:F)`（`scripts/interventions.py` の説明を参照）。
- オーナーが筋・配置・引きを変えたら（owner:A）、先にメモを直し、次に本文の筋を直した版を作る。文の磨きはそのあと。
